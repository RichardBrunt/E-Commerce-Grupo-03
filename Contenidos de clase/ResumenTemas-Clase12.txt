1. Introducción al Despliegue de Aplicaciones
El despliegue (o deployment) de una aplicación es el proceso de poner una aplicación en producción, es llevar nuestro código de desarrollo a un servidor donde puede ser ejecutado 24/7 y accesible desde cualquier lugar con conexión a internet.
Es hacer que nuestra aplicación sea accesible y funcional para nuestros usuarios. Sin despliegue, nuestro e-commerce solo existiría en nuestras máquinas.

Esto incluye:
	Configuración de servidores.
	Gestión de bases de datos.
	Implementación de seguridad y escalabilidad.

Entornos comunes de despliegue:
- Local: Desarrollo en la máquina del programador.
- Testing/QA: Entorno para pruebas controladas.
- Staging: Réplica del entorno de producción para validación.
- Producción: Entorno accesible por usuarios finales.


2. Métodos de Despliegue
A. Despliegue en Servidores Tradicionales (VPS Virtual Private Server)
	Ventajas: Control total sobre el hardware.
	Desventajas: Costo de mantenimiento y escalabilidad limitada.
	Herramientas: Apache, Nginx, MySQL, etc.

	Explicación: Históricamente, el despliegue era un proceso tedioso y propenso a errores. Implicaba configurar manualmente servidores, instalar dependencias, manejar versiones de software, etc. Cada entorno (desarrollo, testing, producción) podía tener diferencias sutiles que causaban que la aplicación funcionara en uno pero no en otro. "en mi maquina funcionaba"
	
	
	Ejemplo:
		Escenario: La empresa tiene su propio servidor o contrata un VPS (Virtual Private Server).
		Imaginen que su e-commerce de Spring Boot requiere Java 17 y MySQL 8.0. Si el servidor de producción tiene Java 11 y MySQL 5.7, ¡su aplicación no funcionará! 

		- Ventajas: Control total, bajo costo si ya se tiene infraestructura.
		- Desventajas: Mantenimiento manual, difícil escalabilidad.	

		1.1 Entornos de Despliegue (Dev, QA/Staging, Prod)
		Para minimizar riesgos, las aplicaciones suelen pasar por varios entornos antes de llegar a producción.
		Desarrollo (Dev): Donde programamos y hacemos pruebas iniciales.
		Control de Calidad (QA / Quality Assurance): Donde se realizan pruebas más exhaustivas (funcionales, de rendimiento, seguridad) por un equipo de "Testing".
		Staging / Pre-producción: Un entorno casi idéntico a producción, usado para las últimas pruebas de aceptación y para asegurar que todo funciona antes del despliegue final.
		Producción (Prod): El entorno real donde los usuarios finales interactúan con la aplicación.
	


B. Despliegue en la Nube (Cloud)
	Plataformas populares:
	AWS (Amazon Web Services)
	Azure: Microsoft Cloud.
	Google Cloud Platform (GCP)
	Ventajas: Escalabilidad, alta disponibilidad (entre comillas con lo que paso el 20/10/25), pago por uso.
	
	Ejemplo:
		Escenario: La empresa quiere escalabilidad y alta disponibilidad.

		Ejemplo con AWS:
			Frontend (React): Alojado en Amazon S3 (almacenamiento estático)
			Backend (Java): Desplegado en EC2 (VMs en la nube. elegir sistema operativo, CPU, RAM y disco.) 
			Base de datos: Amazon RDS (Servicio gestionado de bases de datos relacionales MySQL).

).

		- Ventajas: Escalable, alta disponibilidad, backups automáticos.
		- Desventajas: Costo variable, curva de aprendizaje.	

C. Plataformas como Servicio (PaaS): Heroku, Vercel, Render.

	Beneficios: Configuración mínima, despliegue rápido.
	
	Ejemplo:
		Escenario: Equipo pequeño que busca despliegue rápido sin administrar servidores.

		Ejemplo con Heroku:
			Frontend (React):

			# Configurar despliegue estático o usar Vercel/Netlify
			heroku create ecommerce-frontend --buildpack mars/create-react-app
			git push heroku main

		Backend (Java):

			heroku create ecommerce-backend
			heroku addons:create heroku-postgresql # Base de datos gratis
			git push heroku main

		Dominio personalizado:
		heroku domains:add www.tuecommerce.com

		- Ventajas: Fácil configuración, despliegue en minutos.
		- Desventajas: Límites en planes gratuitos, menos control

3. Proceso Típico de Despliegue
	Desarrollo: Codificación y pruebas locales.
	Integración Continua (CI): 
		Los desarrolladores integran su código frecuentemente en un repositorio compartido (ej. Git).
		Cada integración dispara un proceso automatizado de construcción (compilación del código, empaquetado) y pruebas unitarias/de integración rápidas para detectar errores tempranamente.
		Si las pruebas pasan, el código se considera "integrado" y listo para la siguiente fase.
		- Detección temprana de bugs (evita errores en producción).
		- Mayor velocidad de entrega (releases más frecuentes).
		- Calidad consistente (todas las integraciones pasan por pruebas).
		
	Entrega Continua (Continuous Delivery):
		Después de la CI exitosa, el artefacto de software (ej. un JAR, una imagen Docker) se construye y se almacena en un repositorio de artefactos.
			Un artefacto es cualquier producto final generado durante el desarrollo, aquello que está listo para ser probado, empaquetado, distribuido o desplegado.
		Se ejecutan pruebas automatizadas más exhaustivas (pruebas de aceptación, pruebas de rendimiento, pruebas de seguridad) en un entorno que simula la producción.
		Si todas las pruebas pasan, el artefacto está listo para ser desplegado en producción con solo un clic o una aprobación manual. La decisión de cuándo desplegar queda en manos de un humano.
	
	
	Despliegue Continuo (CD): Automatización del lanzamiento a producción.
		Es una extensión de la Entrega Continua.
		Una vez que el artefacto ha pasado todas las pruebas automatizadas en los entornos intermedios, se despliega automáticamente en el entorno de producción sin necesidad de intervención manual.
		Requiere un alto nivel de confianza en las pruebas automatizadas y en la infraestructura de despliegue.
		El Despliegue Continuo elimina la intervención humana en la fase final de despliegue.
